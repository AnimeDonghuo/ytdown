# YouTube, Terabox, Dailymotion, Rumble, MEGA, Instagram/Facebook and apitera downloader Telegram bot

The bot defaults to **YouTube mode**. Use `/change` to select YouTube-only, Terabox-only, Dailymotion-only, Rumble-only, MEGA-only, Instagram/Facebook-only or apitera-only links; mode settings are per user and reset on restart. Send a YouTube video or public playlist URL in YouTube mode. For a video, it asks the [Samra YouTube API](https://samra-youtube-api.antideploy.com/) for **actually downloadable** MP4 qualities and MP3 audio, then displays toggle buttons. Select as many as you like and tap **Done**. The provider can take 1–2 minutes (the bot waits up to 4 minutes per lookup). For a playlist, the bot first reports the video count (up to 5,000 public entries). Reply with an **inclusive range** such as `1-29` or `200-300` (at most 150 entries per job), then select 360p, 480p, 720p, 1080p, 1440p (2K), and/or 2160p (4K). After Done it discovers only that range of public video IDs with `yt-dlp` and queries the API per video. Qualities absent from an individual API response are skipped, **not replaced with another quality**. Files are transferred and sent one at a time.

Titles come from YouTube first (oEmbed with a `yt-dlp` backup for single videos, and YouTube's playlist entries for playlists). If neither YouTube method returns a title, the bot uses **that video's API title**; only if that is missing does it use the video ID. The filename and Telegram caption end with the chosen quality, for example `Actual Video Title [480p].mp4` and `Actual Video Title [480p]`; audio is labeled `[MP3]`. A subtitle marker such as `[EngSub]` or `[MultiSub]` (also accepted in parentheses, any case) is removed from the title and placed **after** the quality, for example `Episode 15 [360p] [MultiSub]`. For YouTube playlist items, the caption and live-status title show only the title, quality and subtitle tag (no playlist number), while the filename starts with a zero-padded playlist index, for example `02-39 One Way or Another Episode 15 [360p] [MultiSub].mp4` (`002-150` when the total is 150). Terabox names and captions are unchanged. Videos prefer the **API-provided thumbnail URL**; if it returns a mostly white placeholder or fails, the bot tries YouTube's reliable HQ image before max-resolution. If none of those is usable (playlist items, for example, get no API thumbnail), the bot takes one frame from the bounded video sample already captured while streaming, so the preview comes from the video itself. Thumbnails are resized/compressed under 18 KiB (Telegram may silently ignore larger images) and uploaded as a `.jpg` with video dimensions. Videos are sent as streamable MP4 so they **stay playable inline**; a document is only used as a last resort if Telegram refuses the file as video. After a video is delivered, the bot makes one bounded check of the still-image thumbnail Telegram returned (read in 64 KiB requests and capped at 256 KiB, then decoded locally). If that still is missing, unreadable, or white, the bot **replies to the video** with the prepared JPEG as a separate cover photo. A cover problem never causes the video to be uploaded again; it is only logged. This cover check applies to YouTube videos; Terabox thumbnails are unchanged. If Telegram rejects the prepared thumbnail on the send itself, the already-uploaded file is re-sent once without it, because that send did not succeed. Container logs record whether a usable thumbnail was prepared and whether a cover photo was sent. `ffprobe` reads the bounded beginning/end of the actual MP4 to supply Telegram its **duration and real frame dimensions**, without downloading a second full copy; the API duration (including `HH:MM:SS` strings) and thumbnail shape are fallbacks when the stream cannot be probed. Rotated videos have their display dimensions swapped when ffprobe reports a rotation. Ratios cannot be corrected if black/white borders are actually encoded into the source frames. The `ffmpeg`/`ffprobe` package makes the Docker image larger, so a cold Koyeb image download may take longer. Without ffmpeg (for example on BotKeep, which installs only Python packages), the bot logs a startup warning, does not probe the video, and skips the frame-from-sample thumbnail; it still uses the API and YouTube thumbnails.

### Dailymotion mode

Switch with `/change` → **Dailymotion**, then send a Dailymotion video link: `dai.ly/...`, `dailymotion.com/video/...`, `dailymotion.com/embed/video/...`, or a `geo.dailymotion.com/player...?video=...` link. Playlists and user pages are refused. The bot asks the Cloudflare Worker `samra-dailymotion.krishnalucky193.workers.dev` for the title, duration, poster and HLS master playlist, then lists **only the heights that the playlist actually offers** (for example `360p`, `720p`). Pick one or more and tap Done. Each quality is one HLS variant: yt-dlp downloads its segments into a **temporary folder**, ffmpeg remuxes them to MP4, and the file is uploaded from disk as a streamable video, so it stays playable inline. Dailymotion mode does not change YouTube or Terabox behaviour.

Requirements and limits:

- **Hosting:** Dailymotion mode is supported on **Koyeb** (the Docker image includes ffmpeg and ffprobe). It needs ffmpeg and ffprobe on the host. On BotKeep it is unavailable unless those tools exist there; Dailymotion jobs then stop with a clear message, while YouTube and Terabox keep working.
- Each quality needs free disk space of about 1.2× its size estimate, computed from the playlist's peak bandwidth and duration. Temporary files are deleted after each quality. Qualities above the 2,000 MiB Telegram limit are skipped.
- The bot reads the stream playlist from Dailymotion's CDN **from its own IP address**. If the CDN refuses that address, the bot reads the Worker's proxy copy of the same playlist instead, and logs which copy it used. If both fail, the message names the HTTP status (for example `HTTP 403`). A quality that fails during download is reported in the job summary (for example `720p: HTTP Error 403`) and the other qualities still run.
- **Every download route is told what it is downloading, and its file is checked before upload.** yt-dlp is given the stream the extraction found (with the exact protocol and headers it chose), otherwise the playlist URL described explicitly as HLS — never a bare URL, which its *generic* extractor guesses at and can "download" as a few KB of JSON saved under a `.mp4` name. What lands on disk is then verified: a real container header (`ftyp`, Matroska, MPEG-TS…), a size above a floor, and a size that a video of the known duration can actually contain. A file that fails is **discarded, not sent**: the bot tries the next route (the listed playlist, then a fresh extraction from the watch page) and reports the reason when all of them fail.
- **The cover comes from three places, in order:** the poster the API reported, else the thumbnail the extraction found, else Dailymotion's thumbnail endpoint (`…/thumbnail/video/<id>`), which redirects to the JPEG and is simply skipped when the video has none. A missing cover can no longer happen only because the Worker's metadata left the poster empty.
- Private, paid or region-restricted videos fail with the API's message. Nothing is bypassed.
- Cancelling a job stops an active Dailymotion download at its next progress update.


Switch with `/change` → **Terabox**, then send an HTTPS Terabox share URL (including `terasharefile.com/s/...`). The bot calls the [Samrat Terabox API](https://samratbdownload.krishnalucky193.workers.dev/?url=) and shows the formats/qualities **actually returned** for a single file. Select one or several and tap Done. For an exposed folder listing, the bot reports how many files have usable links, asks for an inclusive range, then presents the qualities in that range. Files and selected quality variants are transferred **one by one**, with their real filename extension, MIME, and size (when provided). For video thumbnails the bot tries the file's API preview URL, then the parent listing's preview, applying the same redirect checks, blank-image rejection, and Telegram-compatible JPEG resize used for YouTube. If both fail, it makes one bounded, single-threaded attempt to extract a frame from the video sample already captured during streaming (no second full download); some streams cannot be decoded from this sample, so a thumbnail cannot be guaranteed. If the API reports a folder total but does not expose links for all files, the bot can only process the returned links; it cannot traverse an unlisted folder. Repeated entries with the same file ID and different qualities are treated as one file with multiple choices. The bot refreshes expiring links before transfer when the API supplies `expires_at`. Terabox mode does not accept YouTube links, and vice versa. Each service has its own API: set one with `/changeapi tera <URL>` (see Custom APIs below). Signed links may expire during long jobs, and neither service bypasses private/blocked content.

### Rumble mode

Switch with `/change` → **Rumble**, then send one Rumble video link: `rumble.com/v…-title.html` or `rumble.com/embed/v…`. Channels, search pages and playlists are refused. The bot asks the [Samra Rumble API](https://samra-rumble-api.krishnalucky193.workers.dev/) for the title, duration, thumbnail and the MP4 renditions it lists, then labels each quality by its **real pixel height** (for example `360p`, `720p`, `1080p`). When Rumble lists two renditions at the same height, the bot keeps the one whose stated height matches exactly, so a padded 1081-line entry does not replace the 1080 one. Pick one or more qualities and tap Done. Each quality is a direct MP4 streamed to Telegram as a streamable video, so it stays playable inline. Titles, captions and filenames follow the same title, quality and subtitle-tag format as YouTube. The API's thumbnail is the only cover source; the reply cover-photo fallback still applies. Rumble needs **no ffmpeg**, so it works on BotKeep as well as Koyeb. Rumble does not provide audio, so MP3 is not offered. Rumble links are refused in the other modes, and Rumble mode uses its own API (`/changeapi rumble <URL>`).

### MEGA mode

Switch with `/change` → **MEGA**, then send a MEGA link: `mega.nz/file/…`, `mega.nz/folder/…` (also `mega.io` and `mega.co.nz`, with the `#` key copied along — without it nothing can be listed). The bot calls the [SAMRA MEGA Cloud API](https://samra-mega-api.onrender.com/api/info) with `?url=`, which returns the folder tree plus, for every file, a download URL on the API itself, a streaming URL and the raw `mega.nz` link.

- **Several links at once:** paste up to **10** MEGA file/folder links in one message (anywhere in the text, separated by spaces or new lines). The bot reads them in parallel and shows **one numbered list** covering all of them, so a single range can span several links. A link the API cannot read never sinks the batch — it is named in the prompt (`⚠️ Skipped 1 link(s): link 1 (…)`) and the others are still listed. Each file's entry is prefixed with its link's number (`[2] Module 01/…`) so identical names from different links stay apart.
- **A single file link** offers what that file is (Video / Audio / File) — tap Done and it streams.
- **A folder link** (or any paste holding more than one file) reports `🗂 MEGA folder: 12 files, 3 subfolders.` — or `🗂 3 MEGA links: …` — lists the first files and asks for an **inclusive range** such as `1-5` (up to `PLAYLIST_JOB_LIMIT` per job, default 150). Only files whose kind you selected are transferred, one at a time.
- Files are streamed **straight to Telegram** from the URL the API handed over, exactly like Terabox, so nothing is stored on the host. If the API's download route refuses a file, the bot retries that same file through its other URLs (stream route, then the direct `mega.nz` link) before counting it as failed. Files larger than the bot's limit are reported as *over the size limit* instead of failing mid-transfer.
- The captions are `index/total · title` with the file's real name, extension and MIME, and no ffmpeg is required — so MEGA works on BotKeep as well as Koyeb. The API's own video files carry no thumbnail URL, so a cover is not guaranteed for MEGA.
- MEGA mode accepts only MEGA links, and its API can be replaced with `/changeapi mega <URL>`.

### Instagram/Facebook mode

Switch with `/change` → **Instagram/Facebook**, then send an Instagram post/reel/TV link or a Facebook video link (`facebook.com/watch?v=…`, `/reel/…`, `/videos/…`, `/video.php?v=…`, `fb.watch/…`, a group post, or Instagram `/p/…`, `/reel/…`, `/tv/…`, `/stories/…`). Profile pages, home pages and other sites are refused. The bot asks the DESI worker `samra-insta-fb-api.krishnalucky193.workers.dev` with `?url=` and shows the platform, the title and every downloadable the API listed (labelled by quality, for example **HD Video**, **SD Video**, **Cover**), videos first. Tap one or more and Done.

- **The MEGA API sleeps when idle.** It is a free host, so the first call after a quiet spell can time out or answer `502` while the service wakes up. The bot therefore waits and retries it four times over ~65 seconds (5 s, 10 s, 20 s, 30 s, each attempt getting up to 180 s) and says so in the chat (`⏳ The MEGA API is not answering yet (try 2 of 5)…`) instead of reporting "Could not load this link" at the first hiccup. Only the API's own final answer — a real refusal, a link it cannot resolve — reaches you as an error. The same patience covers the download itself: each of the file's URLs is tried, and if they all refuse without a byte moving, the bot waits 15 s and gives the first one another chance before the file counts as failed.
- **This API is slow** — it scrapes the platforms — so the bot says so up front (`… this API is slow, so it can take a minute`), waits up to **5 minutes** for an answer (`SOCIAL_TIMEOUT`), and retries once if the connection itself drops. It is not cut off early; `/cancel` stops a lookup you no longer want.
- **Several links at once:** up to **5** Instagram/Facebook links in one message are read **in parallel** (faster than one after another on a slow API) and offered as one list, each option numbered by its link (`2 · HD`). Options are capped at 12 buttons; when a paste would need more, the prompt says how many did not fit. A link the API cannot read is named and the rest stay.
- Media is downloaded straight from the CDN URL the API returned, with a browser `User-Agent` and the platform's referer, through the same MTProto streaming pipeline as every other mode. Images are bounded single reads (12 MiB max, HTML/JSON answers refused) and sent as photos; videos are streamed as playable MP4 with a cover from the API thumbnail, or a frame from the video itself when there is none.
- Filenames are `NN-NN title [Label].ext` (`01-03 Sunset timelapse [HD Video].mp4`) so every item of a multi-select stays identifiable; captions carry the title.
- Private or removed posts are refused with the API's own reason. Instagram/Facebook mode accepts only those two platforms, and its API can be replaced with `/changeapi ig <URL>` (`instagram`, `fb`, `facebook`, `insta` also work).

### apitera mode (Moviebox / Anime / Donghua)

Switch with `/change` → **apitera**, then send any link of the [apitera API](https://api.parciv.workers.dev) (`/moviebox/movies?page=2`, `/moviebox/stream?id=…`, `/anime/post?…`) — or use the commands below. `/parciv <link|subject id>` reads one item and offers its qualities as buttons; a catalogue link lists that page instead.

**Browsing by hand: `/latest [sections] [count] [page=2]`** reads page 1 of each section and replies with a numbered list — `✅` for titles your DM already holds, `⬇️` for the rest — plus buttons: **⬇️ Download new**, **⬇️ Download all**, **🔁 Refresh**, **▶️ Auto on/off**. Sections: `movies`, `tv`, `tvshows`, `animation`, `kids`, `recommend`, `anime`, `donghua` (`/latest anime,donghua 4`).

**A listing that hands the file over is downloaded directly.** These families' entries are not consistent: many carry the file URL itself (`url`, `link`, `play`, inside `servers`, inside `episodes`…) and need no lookup at all. The whole entry is scanned for a media link (`http` or `https`, any key, a few levels deep) and, when one is found, that file is downloaded and uploaded — the same thing a leech bot does. An entry with no id and no slug but a file link is still listed and downloaded instead of being skipped, and an entry whose only handle is its API link keeps that link for the lookup. A listing that carries its media list inline (`servers`, `videos`, …) is used as-is too.

**The API's own stream links are files, not pages.** A link of the shape `…/<family>/stream?url=http%3A%2F%2Fsantol.whatbox.ca%3A29318%2F…%2F06-360p.mp4` — the shape a leech command takes — is recognised as the file it carries: sending it to `/parciv` (or to the bot as a bare link) downloads that file and uploads it, and a listing entry that hands one over needs no lookup at all. The name and the quality come from the file inside the link, so `…/KuangWang2/06-360p.mp4` uploads as `Kuang Wang 2 [360p].mp4`.

**Every quality is kept, from both sides.** A title's files come from the API's own answer *and* from the links the listing handed over: they are merged by URL, so a quality that only one of them lists is never lost. A listing entry that carries several links (`qualities`, `downloads`, `videos`, `servers`, …) is kept whole — one source per file — instead of downloading whichever link happened to be first. A title that has an id is looked up first (the API knows its qualities, its cover and its duration); when the lookup finds nothing, the listing's own links are downloaded instead, and a leech link is never looked up at all.

**A link-only source still gets a duration and a cover.** When the API gave neither (which is the case for a bare stream link), the file that was just downloaded answers for both: ffprobe reads its real length (no more `0:00` in Telegram) and one ffmpeg frame becomes the thumbnail. Only when one of them is missing is ffmpeg run, so an API that already answered costs nothing. Without ffmpeg/ffprobe on the host the upload still works: the length is simply unknown and Telegram shows the first frame.

**The `/videos` catalogues are read too.** Each family has a `<family>/videos` page that lists every title with its stream link. Sending that link to `/parciv` reads it as a listing (each entry downloads its own link, no lookup), and the lookup ladder asks `/videos?slug=`, `/videos?id=`, `/videos?subjectId=` and finally `/videos` itself, so a title whose `/post` calls answer without media still resolves. An answer that is a whole catalogue is never read as one episode: the entry for the title — matched by its id, its slug or its name — is the only one used, and a catalogue with no entry for it is reported instead of being mixed with other titles.

**A wrong episode is refused, not uploaded.** When a lookup shape answers for a different title than the listing named (the server-side id pointed somewhere else — Kuang Wang 2 returning Naruto's file is the one the user hit), that shape is skipped and the ladder tries the next one. The check has two parts: the title in the answer is compared against the listing's name (year and episode words ignored, so "Kuang Wang 2" still matches "Kuang Wang 2 Episode 06"), and the folder a CDN URL lives in is checked too — a `/donghua/post?id=…` whose title matches but whose file sits in `…/Naruto/…` is refused for the same reason. Abbreviated URLs (`op-360.mp4` for One Piece) and short tokens are left alone: a 2- or 3-letter folder is not informative enough to refuse on. When every shape returns someone else's data, the message names what each one answered for.

**An answer of an unknown shape still yields its files.** When the known keys (`resources`, `streams`, `videos`, `servers`, …) hold nothing, the whole answer is walked for media files — any key, a few levels deep, including a list of bare links — so a shape this bot has never seen still downloads. A quality label is read from the file's own name, never from a folder or a port: `…/2026/Donghua/KuangWang2/06-480p.mp4` is 480p.

**Anime/Donghua items are looked up by every plausible shape.** These families' post call is not the same in every build of the API (`/post?slug=…`, `/post?id=…`, `/post?url=…`, `/detail?id=…`), and asking with the wrong one answers **200 with a page instead of media** — which used to end as a bare `JSONDecodeError`. The bot now asks each shape in turn until one answers with media, starting with the link a listing handed over, then its slug, then its ids, then its own API URL, and finally the detail call. A listing's `slug`, its own URL and any media URL it carries are all kept for this. When every shape fails, the message names **each shape and what the API answered for it** (`slug: The apitera answer for this episode listed no downloadable files; subject id: answered non-JSON (HTTP 200): <!DOCTYPE html>…`), so a broken call is visible instead of hidden behind a library name.

**A leech answer that is a link is followed.** Some of these routes answer `{"url": …}` rather than the bytes; the bot follows that link (up to two hops) exactly as a leech bot does, and refuses an answer that is a JSON message with no link in it.

**A leech link downloads that file.** Send (or `/parciv`) the API's own file link — `https://api.parciv.workers.dev/donghua/stream?url=<encoded file>` — and the bot downloads exactly that file through the same three routes and uploads it, named after the file (`KuangWang2 06 [360p].mp4`). That is the leech shape: no catalogue and no lookup call is involved. A `?url=` that points at something which is not a media file still falls back to the usual listing/lookup behaviour.

**Any catalogue link works.** Send or `/parciv` any listing-style URL of these families — `/moviebox/tv?page=2`, `/moviebox/recommend`, `/anime/popular`, `/donghua/trending`, even `/moviebox/search?query=paw%20patrol` — and that exact call is read and shown with the same ✅/⬇️ marks and download buttons (`🔁 Refresh` repeats that same link). A URL that points at one item's stream/detail/post call (`/moviebox/stream?id=…`, `/anime/post?slug=…`) still opens that item's qualities instead.

**Search: `/search <words>`.** Every family is asked for that title at once — Moviebox and Donghua (`/<family>/search?q=…`), Anime (`/anime/search?query=…`, the odd one out — it reads `query`, not `q`) — and the matches are listed with the same ✅/⬇️ marks and the same download buttons as `/latest`. When a family has no search call (or it answers without matches), that family's catalogue pages are scanned instead and the reply says so. Narrow it with `/search movies,anime <words>` or `/search <words> sections=movies,anime`; `/find` works too. Matching is by every word you type, ignoring tags, quality, year and language words, so `/search paw patrol` finds `PAW Patrol: The Dino Movie (2026)`. The same title listed in several families is shown once. Anime and Donghua answers come back **one row per episode**, so the reply collapses them to **one button per series** (keyed by the series id, named by the series) — a search for "Kuang Wang 2" shows the series, not 14 episode rows. The Anime search endpoint is unreliable upstream (it sometimes ignores the query), so its results are filtered client-side and it falls back to scanning its catalogue pages.

**Tapping a search match picks the title, then the episodes or the quality.** Every match is now a per-title button; tapping it opens the right next step automatically. For **Donghua and Anime** the title's episodes are shown as a paginated picker — one button per episode, ⬇️ Download selected (N) at the bottom, ◀ Prev / Next ▶ when there are more than 50. The apitera builder's per-series calls are not trustworthy (`/post?id=…` takes an episode id, not the series id, and its `items` are a suggested subset that can belong to another series; `/category?id=…` and `/videos?subjectId=…` are broken or unscoped), so the picker is built from the **family's own search** instead: it is re-asked with a wide `count` and only the rows whose `catId` is the tapped series are kept — a call that is really scoped. Picking an episode downloads exactly the qualities that episode's row listed (no second lookup, which would fetch the same files again). For **Moviebox (movies / tv / animation / kids / recommend / tvshows)** there is no episode step: the tap goes straight to the quality picker — the same card a hand-sent `/parciv` link shows. The same `/search Kuang Wang 2` flow works whether the title came from a donghua, an anime or a moviebox family — the user never has to know which one matched.

**Automatic uploads: `/auto on`.** The watcher checks once immediately, then on a timer (default **every 15 minutes**, up to **3 items per section**), compares every title with the files already in your DM, and uploads whatever is missing — **every quality** the API offers for that subject, with the name the API gave. Each check opens one message of its own: when a batch is queued that message **becomes the normal download status** (`🎬 title · Video 1/3 · progress · /cancel_<job>` — the same card a hand-sent link gets, so you always see what is being processed), and when there is nothing new it is removed again, leaving no clutter. Batches stay in the usual one-at-a-time queue: a running transfer finishes before the next one starts. `/auto off` stops it, `/auto now` checks once immediately, `/auto sections movies,anime,donghua` picks the sections (default: Moviebox movies + Anime + Donghua), `/auto limit 3` the items per section, `/auto every 15m` the pace. `/auto` alone shows the status panel with **▶️ Turn on / ⏸ Turn off / 🔎 Check now / 📄 Latest list** buttons. Settings are per user, live in memory, and only `/auto on` (or the panel button) starts the watcher.

- **The DM check is what keeps it from uploading twice.** The bot reads the chat history (`iter_messages`, up to 300 messages) and compares each catalogue title with every file name and caption it finds, ignoring brackets, quality words, years and episode words — so the catalogue's `PAW Patrol: The Dino Movie` matches the file already sent as `PAW Patrol_ The Dino Movie [Hindi] [Eng Sub] [360p].mp4`. A title already there is skipped and reported (`✅` in a listing, "Already in your DM" in the status). If the history cannot be read, the run still uploads what it found (and logs why).
- **Names carry the title, the languages and the quality**, exactly as asked: the API's own name (its `_360P` suffixes stripped) plus audio tags plus the subtitle language plus the quality — `PAW Patrol: The Dino Movie [Hindi] [Eng Sub] [360p]` as both the caption and `PAW Patrol_ The Dino Movie [Hindi] [Eng Sub] [360p].mp4` as the file name. Moviebox's own title is used first, and never an episode list's name. When the API did not list a language or a subtitle but the file on disk carries them, **ffprobe fills them in** — the bot reads every audio and subtitle stream from the downloaded file, maps the raw codes (`jpn`, `eng`) to the same display names the catalogue uses (`Japanese`, `English`), and the file lands with the right `[Japanese] [English Sub]` even when the API only said "Hindi". The probe is skipped when both API fields are already populated, so a Koyeb free instance does not pay a second ffprobe per file.
- **One source is fetched three ways, in order.** (1) **A direct copy** of the CDN URL — through **aria2c** when the host has it (four parallel connections, resumes, installed in the Docker image; override the binary with `ARIA2_PATH`), otherwise the built-in single GET (both honour the proxy and the signed cookie headers). These CDNs list progressive MP4s, so this needs neither yt-dlp nor ffmpeg and cannot hit a post-process error. (2) **yt-dlp**, for manifests and anything a copy cannot take. (3) **The API's own leech**, `…/moviebox|anime|donghua/stream?url=<source>` — the worker fetches the source itself, which is what works when the CDN refuses the bot (this is the "if yt-dlp fails, use that" route you asked for). If all three fail, the message names each route's reason (`aria2c: aria2c exited 3 …; direct copy: HTTP 403; yt-dlp: …; via the API: …`). The plain `http://` sources these CDNs hand out (with their own port, like `santol.whatbox.ca:29318`) are accepted for media — http or https, as long as the host is a public one — while the API endpoint itself must still be HTTPS.
- **Every quality is tried**: the plain MP4s the API lists per resolution, and the DASH master (`…index_web.mpd`) with the signed CloudFront cookie it needs as a request header. DASH needs **ffmpeg/ffprobe** (the Koyeb Docker image has them); without them the MP4 qualities still work and the DASH entry is reported. A source whose stated size is over the bot's limit is reported as *over the size limit* instead of being downloaded (apitera's 1080p DASH is often ~2.4 GB, above the default 2 GiB).
- Files are downloaded one at a time to a temporary folder, checked (real container, sane size) and uploaded as a **streamable video** with the API's poster as the cover, the API's duration and the quality's frame size. Temporary files are deleted after each upload.
- An automatic batch is a **normal job**: it appears in `/status`, obeys the one-transfer-at-a-time rule, and `/cancel` stops it (the current download stops at its next progress update).
- The API can be replaced with `/changeapi parciv <URL>` (`apitera`, `moviebox`, `mb` also work); a URL that points at one item's stream/detail/post call is refused, because that is not an API base. Proxy mode covers it too: `/proxychk sites apitera` checks proxies against a real catalogue call.

## Custom APIs

Each service calls its own link API with `url=` set to the link you sent:

- **YouTube:** the Samra YouTube API (default `https://samra-youtube-api.antideploy.com/`). It must return the YouTube format list described above.
- **Terabox:** the Samrat Terabox API (default `https://samratbdownload.krishnalucky193.workers.dev/`). It must return the Terabox file listing with download links.
- **Dailymotion:** the Cloudflare Worker (default `https://samra-dailymotion.krishnalucky193.workers.dev/api/info`). It must return `success`, `title`, `duration`, `poster` and an HTTPS `master_m3u8` playlist.
- **Rumble:** the Samra Rumble API (default `https://samra-rumble-api.krishnalucky193.workers.dev/`). It must return `success`, `title`, `thumbnail`, `duration` and a `streams` list whose entries have `type` `video`, `format` `mp4`, a `real_height` or `height`, and an HTTPS `url`.
- **MEGA:** the SAMRA MEGA Cloud API (default `https://samra-mega-api.onrender.com/api/info`). It must return `success` with `folders` and `files`, every file carrying a name, a size and at least one HTTPS URL (`download_url`, `stream_proxy` or `direct_mega_link`).
- **Instagram/Facebook:** the DESI worker (default `https://samra-insta-fb-api.krishnalucky193.workers.dev/`). It must return `status`, `platform`, `title`, `thumbnail` and a `downloads` list whose entries have `quality`, `format`, `type` and an HTTPS `url`.
- **apitera:** the apitera API (default `https://api.parciv.workers.dev/moviebox`). Its catalogues return entries with `subjectId` and `name` (Moviebox) or `id`/`catId`/`series` and an inline `streams` list (Anime/Donghua); the Moviebox pages nest the titles inside `sections[].items`. A family's search is `<family>/search?q=…` for Moviebox and Donghua and `<family>/search?query=…` for Anime, and is optional — without it (or when it answers without matches) `/search` scans the catalogue pages (`/moviebox/<section>?page=N`, `/anime/new?page=N`, `/donghua/trending?page=N`); `/moviebox/stream?id=` must return `resources` (or `streams`) with `url` and `resolution`; Anime/Donghua posts return their media either as a `streams` list or as the flat `video_url`/`video_url_hd`/… keys, and the per-episode lookup is refused when it answers for a different title. The root URL (`https://api.parciv.workers.dev`) works too. Reads are retried once or twice on the transient failures the upstream is known to throw (a 200 with a truncated body).

To use your own API for one service, for example Dailymotion:

1. Send `/changeapi daily https://your-api.example.com/info` (or `/changeapi daily` and then the URL).
2. Send a Dailymotion link. The bot now asks your API.
3. Send `/changeapi daily reset` to return to the built-in API.

A custom API must be public HTTPS, must not point at a media link (YouTube, Rumble, MEGA, Instagram, Facebook…), and must return the same JSON shape as the built-in one. If it does not, the bot reports that the link could not be loaded. Your custom URL is kept in memory only and is shown back to you by `/apis` and `/changeapi show`, so do not put secrets you do not want in your chat history into the URL. The Koyeb deployment needs no extra settings for this.

## Koyeb deployment (Docker)

1. Create a Telegram bot with BotFather; keep its bot token secret. Get an **API ID** and **API hash** for your Telegram application from [my.telegram.org](https://my.telegram.org/).
2. Create a Koyeb Web Service from this repository using its `Dockerfile`. Select the free instance and **one replica only** (multiple instances of the same bot can duplicate work).
3. Configure Koyeb **secret environment variables** `BOT_TOKEN`, `API_ID`, and `API_HASH`. These are required. Do not commit them to the repository. **No string session or user account login is needed**: Telethon logs in as the bot using an in-memory MTProto session and your bot token. A restart creates a fresh login session.
4. Use service port **8000** (`PORT` can override it) and the HTTP health check **`/healthz`**. Telegram updates and uploads use MTProto; the web port is only for Koyeb health checks. No webhook is needed.
5. Optionally set `MAX_FILE_MB` (default 2000, clamped to 1–2000), `MAX_RANGE_VIDEOS` (default 150, clamped to 1–150), and `UPLOAD_IN_FLIGHT` (default 2, clamped to 1–3 upload parts). Add `PROXY_LIST` (and optionally `PROXY_ENABLED=1`) to give the bot a proxy pool that survives restarts. Send `/start` to your bot.

### BotKeep deployment (plain Python, no Docker)

BotKeep runs the bot directly from `requirements.txt`; it does not use the `Dockerfile`, and it cannot install system packages such as ffmpeg with apt.

1. Create a Python workload from this repository (GitHub or ZIP deploy). Use the repository root, which contains `requirements.txt`. Use Python **3.11 or newer** if BotKeep offers a choice; the Dockerfile uses 3.11.
2. Install command: `pip install -r requirements.txt`
3. Start command: `python -m ytdown`
4. Add the secret environment variables `BOT_TOKEN`, `API_ID`, and `API_HASH` in the BotKeep panel. Do not commit them or a `.env` file. As on Koyeb, no string session or user login is needed.
5. Run one instance only, as on Koyeb, so the bot does not duplicate work.

Notes for BotKeep:

- **No public port is required.** Telegram traffic uses MTProto. The `/healthz` endpoint starts only if the platform gives the process a port (`PORT`, default 8000). If the port cannot be bound, the bot logs a warning and keeps running. Do not rely on `/healthz` to keep the workload alive.
- **ffmpeg may be missing.** At startup the bot logs a warning naming any missing `ffmpeg`/`ffprobe`. Without them there are no probe-based durations or frame thumbnails: durations come from the API and thumbnails come from the API or YouTube images, with the same safety checks as before. Uploads still work. If the platform does not provide ffmpeg, expect this degraded mode.
- **Native packages.** `cryptg` is an optional native accelerator. If its install fails on BotKeep, remove the line from `requirements.txt`; the bot falls back to pure-Python encryption and still works, only more slowly.
- **Rumble works on BotKeep.** It needs only the Rumble API and direct MP4 downloads, with no ffmpeg.
- **apitera works on BotKeep for its MP4 qualities.** Only the DASH master needs ffmpeg/ffprobe (for muxing); those entries are reported as unavailable without them, and every MP4 quality still uploads. Automatic runs need the bot online at the check time, of course.
- **Dailymotion is Koyeb-only for now.** Dailymotion needs ffmpeg and ffprobe, which the Koyeb Docker image provides and BotKeep may not. Without them, Dailymotion jobs fail with a clear message while YouTube and Terabox keep working. Dailymotion temporary files use the host's disk, so check the free storage before downloading long videos.
- **Ephemeral state.** Like Koyeb, `/changeapi` settings, the queue, and status history are in memory and reset on a restart or redeploy.
- Keep the BotKeep console open or check it when a job seems stuck. Logs show lookup retries, refused links that were refreshed, and any cover-photo fallback.

## Large uploads and free-tier limits

The bot uses **MTProto rather than the standard Bot API upload endpoint**, so its configured per-file limit is **2,000 MiB** (about 2 GB), instead of 50 MB. With 512 KiB parts this is exactly 4,000 parts, the Telegram client upload-part boundary; larger sizes such as 2,047 MiB would need too many parts and are rejected before transfer. If a media URL supplies `Content-Length`, the bot streams bounded 512 KiB chunks directly from the provider into Telegram's MTProto upload; it does **not** save the whole video on Koyeb or load it into RAM. It checks the declared and actual size. The transfer must remain accessible throughout the upload. If a Terabox URL omits `Content-Length` but the API supplied `size_bytes`, that size is checked against the actual stream and used for bounded streaming. Otherwise, a missing length temporarily spools files up to **64 MiB** to discover their size, and skips larger unknown-size files. Redirects must remain on public HTTPS hosts.

Uploads near the 2,000 MiB limit can take a long time and consume significant bandwidth; Koyeb's free-tier network, runtime, and resource limits may interrupt them. Success depends on the provider link staying valid and the Telegram servers accepting the media. A single global transfer slot and four waiting jobs bound concurrent resource use. You can send another link in your active mode and choose its formats while an earlier job is running; each completed selection joins the FIFO queue. One pending format-selection panel per user is supported. The global queue holds at most five jobs total (one active plus four waiting). At most two link lookups run concurrently; playlists are counted using flat metadata and individual video API lookups remain sequential. Temporary files are deleted after use; jobs and selections are in memory and are **not restored** after a restart. Playlist API lookups run sequentially and can take 1–2 minutes *per video*, so a 100-video selection can take a long time. The final summary lists why items were skipped, for example `item 1: lookup HTTP 403` or `item 3 720p: HTTP 403`. Between playlist items the bot pauses about 2 seconds before each lookup. A lookup that fails with a rate limit (HTTP 429), a server error, or a non-JSON provider page is retried up to three times with short waits (4 s, then 12 s); other client errors are not retried. When the provider refuses a download link (HTTP 403, 404, or 410) before any bytes have been sent, the bot requests one fresh link from the API and retries that quality once. A link refused after transfer has started is not refreshed and is reported as failed. The bot does not transcode or split files.

### Live status and speed

Each time you tap **Done** after choosing qualities, the bot posts a **new combined live status** showing the newly queued job and any running/queued jobs. The status lists **running and queued jobs only**: finished, failed, and user-cancelled jobs never appear in it, regardless of how long ago they ended. It deletes the old status/selection panels where Telegram permits it. `/status` (or `/queue`) likewise replaces the old message with a fresh combined status. Each job displays a tappable `/cancel_JOBID` command rather than a Cancel button. YouTube status titles include the subtitle tag after the quality, for example `🎬 One Way or Another Episode 15 [360p] [MultiSub]`. The status edits automatically approximately every **12 seconds** and has **Refresh all**, which edits immediately and resets the automatic timer; repeat taps within two seconds are ignored to avoid flood waits. The dashboard includes progress bars, source and Telegram bytes, upload speed, ETA, and queue position. If posting a new dashboard fails, the job's selection message still shows its own live progress. Dashboard state is bounded to 100 users; an idle dashboard may be evicted when this limit is reached, and `/status` reopens it. During an API lookup or playlist discovery, size and ETA are not yet known. Resource readings use the **container cgroup CPU quota and RAM usage** (not the Python process alone) when available; Koyeb's dashboard may show a different sampling window. If cgroup data is unavailable, the status says so rather than claiming it matches Koyeb.

The optional native **`cryptg`** accelerator reduces MTProto encryption CPU usage. Large and small known-size uploads pipeline **two 512 KiB parts** by default instead of waiting for each part's round trip. This uses about 1 MiB of in-flight part data per job and keeps the single global transfer limit. On a particularly CPU-constrained free instance, set `UPLOAD_IN_FLIGHT=1`; for faster networks, 2 is the recommended starting value (3 is the maximum). Throughput is still limited by the provider, Telegram, and Koyeb; this cannot guarantee a particular speed.

### Proxy pool (`/proxychk` and `/proxy`)

Every user has a **private proxy pool**, and it covers every mode, including Dailymotion, Rumble, MEGA and Instagram/Facebook. `/proxychk` asks for a list; paste proxies in a message (a few hundred fit) or send a **`.txt`/`.csv` file** for large lists (up to `PROXY_CHECK_MAX`, 2 MiB per file). Accepted forms are `host:port`, `host:port:user:pass`, `user:pass@host:port`, `host port`, and URLs such as `socks5://user:pass@host:1080` (`http`, `https`, `socks4`, `socks4a`, `socks5`, `socks5h`, and the `socks` shorthand are understood). Comments (`#`, including inline ones) and duplicates are ignored.

By default each proxy is checked against the **Dailymotion API** and the **Rumble API** with `PROXY_CHECK_WORKERS` parallel workers; both services are probed over the same proxy connection, so the connection count stays bounded. The probe is the API you have configured — the built-in one, or whatever `/changeapi` points that service at — so a pass proves the proxy can really reach **your** provider. Only a real **JSON** answer counts: an HTML login/captive-portal page, an empty reply, or a non-200 answer never passes, however fast it arrives (if a configured API URL is unusable, the check falls back to that site's `robots.txt`). YouTube and Terabox are **not** checked unless you ask for them. Progress is edited into the message (`… 412/1000 done · Dailymotion 31 · Rumble 34`), and results are stored **as they arrive**, so `/proxychk stop` (or `/cancel proxy`) keeps what has already been tested. A proxy counts as reachable when **at least one** site answers through it, and each site is recorded separately, so a proxy blocked by one service stays usable for the other.

- `/proxychk url https://api.example.com/healthz` — **add your own public HTTPS URL** to the checks (for example an extra `/changeapi` provider host), alongside the service APIs; a URL that belongs to a known site replaces that site's probe instead. Probe bodies are requested with `Accept-Encoding: identity` and never auto-decompressed, an HTML login/captive-portal page is treated as a failure, never a pass, and your own URLs may answer empty (200/204) or with plain text/JSON.
- `/proxychk sites youtube,terabox` — test exactly the sites you name (`dailymotion`, `rumble`, `youtube`, `terabox`, `mega`, `social`, `apitera`); `/proxychk sites default` restores **Dailymotion + Rumble**. `PROXY_CHECK_SITES` sets the same default at boot.

**Too-fast guard.** A proxy cannot reach a remote site in a few milliseconds, so an answer that arrives that quickly did not come from the site — it was cached, forged, or served by something on the local network. Any reply faster than `PROXY_MIN_LATENCY_MS` (**20 ms** by default) is therefore counted as a **failure**: the site gets a `too fast (7 ms < 20 ms)` result instead of a pass, and a proxy whose every reply is that fast lands in the pool as dead. The report calls it out — `⚡ 4 replies arrived under 20 ms and failed automatically — that is too fast for a real round trip through a proxy (for example http://1.2.3.4:8080)` — and `/proxychk fast <ms>` changes the threshold for your checks (`/proxychk fast off` disables it if your proxies really are that close).

**When the API itself is the problem.** A proxy can be fine while the API behind it is not. If the API answers with an error or a non-JSON page for every proxy, the report says so — `⚠️ 3 proxies reached the API but got no usable answer (HTTP 500, not a JSON API answer ×3). They stay in the pool instead of being marked dead` — and adds that many identical answers usually mean the provider is failing, so `/apis` and `/changeapi` are worth a look. Such a check keeps each proxy's **previous** status instead of killing it. Provider traffic behaves the same way: when Dailymotion refuses the Worker proxy playlist (`HTTP 403`) or the Rumble API answers `HTTP 500`, the bot now reads the video through `yt-dlp` on the same proxy — Dailymotion also retries the refused quality from the watch page, and never uploads a file that is not a playable video (see *Dailymotion mode*) — instead of failing the job; if every route fails, the API's own message is kept in the error.

**Saving the pool for later.** `/proxychk export` (equally `/proxy export`, or the **📄 Export live** button on the panel) sends the whole pool back as `working_proxies.txt`: every **live** proxy, fastest first, with its site marks in a comment (`http://1.2.3.4:8080  # DM,RU`). `/proxychk export all` also includes the untested ones; proxies marked dead are never exported. Paste that file into `/proxychk` after a restart and those proxies come back **live with their marks already set** — no re-check needed — and the reply says how many carried marks. To get them back automatically at every start instead, put the same lines in the `PROXY_LIST` environment variable (it reads the marks as well).

A check reply reports how many proxies were reachable, the per-site counts, and each working proxy with its **site marks** (`YT,DM,RU`), keeps working ones as live and dead ones as dead in your pool, and sends `working_proxies.txt` back when more than 20 work — that file carries the marks as comments and can be pasted back after a restart unchanged. The pool is bounded by `PROXY_POOL_MAX` (5,000 by default); anything beyond that is reported, not stored.

`/proxy` posts a panel with **ON / OFF**, **Re-check pool**, **Pool status**, **Remove dead** and **Clear pool** buttons:

- **ON** routes *your* provider traffic — YouTube/Terabox/Dailymotion/Rumble API lookups, `yt-dlp` playlist discovery and titles (`oEmbed`), thumbnails, the Dailymotion master-playlist fetch and its HLS remux (`yt-dlp` proxy option), Rumble's direct MP4 downloads, and the media streams — through your live proxies. Telegram/MTProto traffic is **not** proxied. The bot's other users are unaffected by your setting.
- Requests for a known site skip proxies that were checked and **failed for that site**: a Dailymotion or Rumble request prefers a proxy marked `DM`/`RU`, which is exactly what the default check measures (the service's own API). Proxies that were never checked still count as candidates, and because YouTube is no longer checked by default, YouTube traffic simply uses any live proxy.
- Each request tries up to three live proxies (round-robin). A proxy that cannot be reached, times out, refuses the tunnel, replies with a proxy-level HTTP error (407/502/503/504) or makes `yt-dlp` fail with a network/anti-bot error gets a strike; after **two consecutive failures** it is **removed from the pool** and the request is retried with the next live proxy. `PROXY_FAIL_LIMIT` changes the limit.
- When no usable proxy is left, requests continue **without a proxy** by default and the dashboard shows the fallback count. Set `PROXY_STRICT=1` to fail instead of falling back, e.g. to avoid ever using the host's own address.
- **Re-check pool** re-tests the stored list against every configured site; **Remove dead** deletes proxies marked dead; **Export live** sends the pool as a paste-back `.txt` (see *Saving the pool for later* above); **Clear pool** empties it and turns proxy mode off. The panel shows which sites are tested, the current too-fast threshold, and how many proxies reach each site: `Reaching: Dailymotion 18 · Rumble 20`.
- `/proxy on`, `/proxy off`, and `/proxy clear` work without the buttons; the live dashboard adds a `🌐 Proxy:` line while proxy mode is on.

Provider links are still validated as public HTTPS URLs before use, exactly as without a proxy; with a proxy in the middle, name resolution for the request happens at the proxy, not on the host. Telegram/MTProto connections always go direct, so the bot itself remains reachable even when every proxy fails.

Environment variables (all optional): `PROXY_LIST` (newline/comma separated proxies that seed every user's pool; the lines `/proxychk export` writes — marks and all — work here), `PROXY_ENABLED=1` (start with proxy mode on), `PROXY_STRICT=1` (never fall back to a direct connection), `PROXY_POOL_MAX`, `PROXY_CHECK_MAX`, `PROXY_CHECK_WORKERS` (default 24), `PROXY_CHECK_TIMEOUT` (seconds, default 8), `PROXY_CHECK_SITES` (`dailymotion`, `rumble`, `youtube`, `terabox`, `mega`, `social`, `apitera` — any combination; default `dailymotion,rumble`), `PROXY_CHECK_URL` (public HTTPS URL the check should use), `PROXY_MIN_LATENCY_MS` (default 20, `0` disables the too-fast guard), `PROXY_FAIL_LIMIT` (default 2), `ARIA2_PATH` (the aria2c binary the apitera downloads should use), `PARCIV_AUTO_INTERVAL` (seconds between automatic apitera checks, default 900) and `PARCIV_AUTO_LIMIT` (items per section per run, default 3). Pools, proxy mode, and check results live in memory and reset when Koyeb restarts; `PROXY_LIST` is the way to keep a fixed pool across deploys.

**State persists in MongoDB when `MONGODB_URL` is set.** The apitera state (which titles the bot has already uploaded, each user's `/auto` settings, the chosen sections, the `/changeapi` overrides) is normally in memory. When `MONGODB_URL` is set on Koyeb (anywhere Mongo's `AsyncIOMotorClient` accepts — `mongodb+srv://…` or `mongodb://…`), the bot uses an async `motor` connection instead. The settings are reloaded on startup so a redeploy keeps each user on the same configuration, and the upload log is updated on every successful send so the watcher does not re-upload the same file after a restart. The store is best-effort: a failed write is logged and the in-memory state stays authoritative. When the env var is absent or Mongo is unreachable, the bot keeps working exactly as before — development does not need a database.

**Crunchyroll is not supported.** Its streams are Widevine-encrypted, and reading them means asking Widevine for the content keys with a real CDM device file and then decrypting the video (what `LastPerson07/Crunchyroll-Downloader` does with `pywidevine` + `mp4decrypt`). That is DRM circumvention: it breaks Crunchyroll's terms, risks the account and the host, and would need a CDM that cannot be shipped or replaced once revoked. A Crunchyroll link is **recognised** and answered with that explanation instead of a confusing parse error — including `beta.crunchyroll.com` and `/series/` links — and it is never accepted as an `/changeapi` endpoint. For offline viewing, use the Crunchyroll app's own downloads with a premium account.

Only download media you have permission to use. Private, region-blocked, or age-restricted videos are not bypassed.

## Commands

- `/start` or `/help` — usage instructions
- `/change` — YouTube / Terabox / Dailymotion / Rumble / MEGA / Instagram-Facebook / apitera mode buttons; mode changes affect future links, not queued transfers, and clear any stale `/changeapi` URL prompt
- `/status` or `/queue` — replace the old status with one live dashboard showing running and queued jobs only; selecting a quality and tapping Done also posts a fresh dashboard automatically
- `/cancel` — list your running/queued job IDs, any running proxy check, and tappable `/cancel_JOBID` commands without stopping anything; `/cancel_JOBID` stops exactly that job, even if it is running. `/cancel JOB_ID` remains supported. `/cancel lookup` stops a pending link lookup and `/cancel proxy` stops a running proxy check. Sending a plain proxy list to the bot (not a media link) also starts a check. If no jobs are active, `/cancel` clears a pending selection or lookup.
- `/apis` — lists the API used for YouTube, Terabox, Dailymotion, Rumble, MEGA and Instagram/Facebook for your account (built-in or your custom URL). `/apis remove yt|tera|daily|rumble|mega|ig` restores one service's built-in API. Built-in APIs cannot be deleted.
- `/changeapi` — shows the usage. `/changeapi yt|tera|daily|rumble|mega|ig|parciv <URL>` sets your own public HTTPS API for that service (`yt` = YouTube, `tera` = Terabox, `daily` = Dailymotion, `rumble` = Rumble, `mega` = MEGA, `ig` = Instagram/Facebook, `parciv` = apitera; `youtube`, `terabox`, `dailymotion`, `rum`, `mega.nz`, `insta`, `fb`, `facebook`, `apitera`, `moviebox` also work). `/changeapi yt` on its own asks for the URL. `/changeapi show` lists all of them; `/changeapi <service> reset` restores one built-in API; `/changeapi reset` restores all of them. A bare `/changeapi <URL>` still sets the YouTube API. Changes affect **future** selections; already selected or queued jobs keep the API they started with. A media link sent while the prompt is open is treated as a media link, not as the API URL. Settings are in memory and reset after a restart.
- `/auto` — the automatic apitera uploader: `/auto on|off`, `/auto now`, `/auto sections movies,anime,donghua`, `/auto limit <1-10>`, `/auto every 15m`; the panel has Turn on/off, Check now and Latest list buttons.
- `/latest [sections] [count] [page=2]` — list page 1 of the apitera catalogue now, marking what your DM already holds, with buttons to download the new titles or everything listed.
- `/search [sections] <words>` — find a title in every apitera family at once (searches the API, falls back to scanning the catalogue pages), with the same download buttons as `/latest`.
- `/parciv <apitera link or subject id>` — read one Moviebox item (or an Anime/Donghua post) and pick its qualities; the API's own file links (`/<family>/stream?url=…`) download that file directly.
- `/debug <apitera URL>` — show what an endpoint really answers: its keys, the lists it holds and its first two entries (values cut to 80 characters). This is how a wrong call shape or an unknown field name becomes visible instead of a bare error. A link that is the video file itself is named as such (with the file it carries) instead of being fetched.
- `/debug <section> <id or slug>` — try every lookup shape for one item and report what each one answered (`✅ slug: 1 file(s) — 360p`, `❌ id: The apitera answer for this episode listed no downloadable files.`). This is the fastest way to see which call shape an API build actually serves.
- `/proxychk` — send a proxy list (text or `.txt` file) to test it against **Dailymotion + Rumble**; working proxies join your pool with their site marks and dead ones are marked. Replies faster than the too-fast threshold fail automatically. `/proxychk url <https://…>` also checks your own API host, `/proxychk sites youtube,rumble` picks the sites, `/proxychk fast <ms|off>` tunes the too-fast guard, and `/proxychk stop` cancels a running check.
- `/proxy` — proxy mode ON/OFF buttons plus pool status, re-check, remove-dead and clear actions; `/proxy on|off|clear` also work directly
- `/limits` — current upload, playlist-range, queue, and proxy limits

In YouTube mode, a watch URL containing `list=` is treated as a playlist; remove that parameter to download only the video. `youtu.be` links are treated as single videos. Playlists must be publicly discoverable through `yt-dlp`; keep `yt-dlp` updated if YouTube changes its site.
